# Decisions, trade-offs, and the numbers that come with them

Everything below is a choice a reviewer can question, with the alternative considered
and the reason it lost.

## 1. The queue is Postgres, not a broker

**Chosen:** tickets in Postgres, claimed with `FOR UPDATE OF c SKIP LOCKED`.

**Why not Redis Streams / RabbitMQ:** money lives in the same transaction as the ticket.
Charging and completing must be atomic with the ticket state change; putting the queue in
Postgres makes that one transaction instead of a distributed protocol. We also avoid a
second failure domain.

**Cost:** polling latency (~0.4 s idle) and table churn. Both are irrelevant at this
scale and disappear behind the two named workers.

## 2. Tickets are `(job, stage, shot)`, with `deps`

**Why:** a crashed worker must resume at node granularity, not re-run a job. `deps` makes
the pipeline a persisted graph; the claim query only picks tickets whose deps are `done`.

**Cost:** more rows, more bookkeeping. Paid for by durability and by making
regeneration, retry and cancel all local edits to the same structure.

## 3. Reservation headroom = quote + 2 × shots × image_price

The only unbounded cost in the pipeline is the consistency loop. Capping it at 2
regenerations per shot makes the worst case calculable, so we can reserve it up front and
guarantee the account cannot go negative mid-job. Unused headroom is released at
settlement. If a third regeneration is needed, the shot is marked `inconsistent` and the
job completes with it flagged rather than spending money the customer did not approve.

## 4. Settlement waits for quiet, not just terminal

`finalize.maybe_finalize` releases the reservation only when the job is terminal **and**
no ticket is `pending`/`running`. Releasing on the terminal transition alone would race a
final in-flight charge against the release: the account could briefly hold less than it
owes. The invariant we test is the whole story: `reserve == charged + released`.

## 5. Customers pay quoted prices, never provider prices

A fallback provider changes cost of goods, not the price. Charges always use
`price_table` per stage. This makes `quote == charge` an assertable customer invariant
and keeps provider churn out of the money path. Provider cost accounting is a later,
separate ledger.

## 6. Clip cache key uses the logical router

Keying by the winning provider would evict a cached clip the moment that provider goes
down — the exact moment you want the cache. The logical `router` key reuses cached clips
across fallbacks. Downside: if provider tiers must be honoured strictly, a cached
"cheap" clip would serve even when a premium provider would be chosen. Today providers
are mock cost/quality bands, so the trade is acceptable and stated.

## 7. Provider failure: 402 → cooldown 120 s → fallback

`402` marks the provider down in Redis for 120 s (short enough to recover from a blip,
long enough to avoid hammering a sick provider) and emits **one** event per outage.
Retries (timeout + exponential backoff with jitter) happen before the fallback so
transient errors do not flip providers. Non-402 errors also fall back but mark the shot
`degraded`.

## 8. Lease 30 s, heartbeat 10 s, 3 attempts, then bury

Mock stage latency is 1–5 s; a full slow path with 3 provider retries stays under ~20 s.
The lease (30 s) covers the slowest call with margin; heartbeats at ⅓ of the lease; the
sweeper requeues anything whose owner stopped heartbeating. Burying after 3 attempts
turns an infinite retry loop into a visible `failed` ticket instead of a silently
spinning worker. Measured: the takeover test finishes an interrupted 5-shot job in 41.5 s
wall clock with zero duplicate charges.

## 9. Consistency threshold 0.75

See `docs/calibration.md` (generated by `tools/calibrate.py`). The mock embedding space
is bimodal (consistent ≈ 0.991, drifted ≤ 0.504), so on 4000 labelled shots every
threshold between 0.60 and 0.98 is perfect, and the cost-optimal band's midpoint is
0.74. We ship 0.75 and say plainly that the *method* transfers to real embeddings while
the number itself must be recalibrated.

## 10. Admission: fixed window 30/min, 2 active, replays bypass

Fixed-window is simpler than sliding-window and adequate at 30/min; the active-job cap is
the real backstop against unbounded fan-out. The idempotency lookup happens *before*
admission checks so a client retrying the same `Idempotency-Key` is never 429'd.

## 11. Slot semaphores: Redis sorted sets with expiring leases

`ZADD sem:<pool> <now+60s> <token>` under a Lua script that first prunes expired
holders. A worker that dies mid-call loses its slot after at most 60 s; there is no
manual "release on crash" path to forget. `io` = 8 (two workers × four provider calls),
`cpu` = 2 (compose/transcode kept serial-ish). Both are one-line env overrides and
reported in `/metrics` as `pipeline_slots_in_use`.

## 12. Metrics scrape Postgres, not process counters

A Prometheus scrape hits one HTTP process; the work is in two workers. Counters inside
processes would need federation/aggregation and reset on restart. Reading durable state
at scrape time makes `/metrics` a system-wide view with no extra infra. Latency
histograms per provider are the honest gap here (they need a place to accumulate; the
events table would serve).

## 13. SSE reads the same events table the UI reads

No Redis pub/sub: the browser polls the durable log via SSE, supports
`Last-Event-ID`/`?last_id=`, and a refresh reconstructs history from the same rows. One
source of truth for progress. The test `tests/test_sse.py` proves a reconnect replays
the log without gaps or duplicates.

## Known cuts (said out loud, not hidden)

1. Regeneration runs inline in the `check` handler instead of enqueueing tickets. It is
   idempotent and capped, but holds a ticket through up to 3 provider calls.
2. No auth; `user_id` defaults to `demo`; the top-up route is demo-only and labelled.
3. Cancellation does not pass cancellation into in-flight `httpx` calls; money stays
   exact because settlement waits for them.
4. The mock embeddings are synthetic and bimodal; calibration is a methodology demo.
5. Compose was written for the deliverable but this build machine has no Docker; the
   test/demo numbers come from `run_local.py` against real Postgres 16 + Redis 7 with the
   same schema and code.
